Verdict: no injection, no Critical/High in the security sense. The probe, wiring, tests, vendoring and release are correct and well tested. The threat model's attacks 1, 3, 4 (by default) and 5 hold. What the review adds is two gaps in the signal and the advice: a host that answers 403 to everything reads all-green (the spec's own anti-goal), and the fix hint can tell an operator to deny a whole parent directory.

## Blocking

1. `dist/Makefile.netdust:774-775` and `skills/devops/SKILL.md:221-222` — the fix hint denies the PARENT DIRECTORY of any served file: a served `/app/debug.log` prints `location ^~ /app/ { deny all; return 404; }` and a served `/wp-content/debug.log` prints `location ^~ /wp-content/ …`. On a Bedrock or stackedWP site those directories hold every theme, plugin and upload; pasted into Ploi with a restart it takes the site's assets down, and `WP_DEBUG_LOG` left on is exactly what makes `debug.log` the first served path. The skill text says "deny the directory" with no exception, so `/.env` becomes `^~ /`. The eval exercises only the `/app/logs/index.html` shape, where the directory rule is right. Fix: the directory rule (`location ^~ <dir>/`) only for the log-directory markers (`/app/logs/index.html`, `/wp-content/logs/index.html`) and for `/.git/HEAD` (`^~ /.git/`); `location = <path>` for every other served path; the same sentence in the skill; a test with `/app/debug.log` served expecting `location = /app/debug.log`; a second eval case for `/wp-content/debug.log` whose signature rejects `^~ /wp-content/`. [whole-branch review: Critical; security-sentinel: M2]

## Should fix

1. `dist/scripts/health-exposure:33` and the control request `:66-68` — an environment that answers 403 to EVERYTHING (Cloudflare bot challenge, a WAF rejecting the `netdust-health` user agent, an IP allow-list, or the probe's own requests getting the operator banned by Wordfence or fail2ban) reads all `not served`, exit 0: the spec's anti-goal. Reproduced against a fixture answering 403 to every path. Fix: a control that answers anything other than 404 or 410 (and not 200 or 000, which are handled) marks the environment walled, every path `not conclusive`, one yellow line naming the control code; a `WALL=1` fixture mode and a test. [both reviewers: whole-branch #2, security-sentinel M1]
2. `plugins/netdust-devops/.claude-plugin/plugin.json:4` — a typo this diff introduced: `0.13.0:promote` (the space after the colon was lost when the `0.14.0:` line was prepended); the marketplace entry has `0.13.0: promote`. [whole-branch #3]
3. `dist/scripts/health-exposure:18` — mitigation 4 (no redirect followed) depends on the absence of `-L`, which a `~/.curlrc` can add (reproduced: the probe followed a redirect; `-k`, `-x` and `-u` could be added the same way). Fix: `curl -q` as the first argument. [security-sentinel L1]
4. `dist/scripts/health-exposure:12,69` — `URL_RE` admits userinfo: `https://admin:s3cret@host` passes, the heading echoes it into the terminal or CI log, and curl sends it; `http://127.0.0.2:1@127.0.0.1:PORT` is host confusion. Fix: drop `@` from `URL_RE` (a rejected url gives the yellow "skipped, url is not valid" line); a test. [security-sentinel L2]
5. `dist/scripts/health-exposure:56,75` and `dist/Makefile.netdust:634` (`doctor`) — a box without `curl` prints `unreachable` for every environment and exits 0, and a missing `scripts/site` or PyYAML (site reader exits 2) prints nothing and exits 0. The operator would suspect the sites, not the tool. Fix: a `command -v curl` guard that prints one yellow line and says so; capture `"$SITE" environments` into a variable, check its status, print "site.yml unreadable"; add `curl` to the `doctor` tools loop. [security-sentinel L3; whole-branch #4]
6. `dist/Makefile.netdust:773` — the hint's `awk '$2=="served"{print $1; exit}'` matches the first line whose second field is `served`, so a skipped `deny_paths` entry or an environment named `x served` mis-steers the hint (reproduced: `^~ ./`); no injection, but a wrong hint. Fix: `awk '$1 ~ /^\// && $2=="served"{print $1; exit}'`. [security-sentinel L4]
7. `tests/test-makefile.sh:320` — the "prints no body" assertion checks `EXPOSURE-BODY-MARKER`, served on a HEAD request and so never transferred: it cannot fail. Fix: assert that the body of the GET-retried path (`/.git/HEAD` answers `ref: refs/heads/main`) is absent from the output. [whole-branch #6]
8. `evals/devops-exposure-probe-2026-11-05-cases.json` — the signature's last clause ("does not hand-edit the server outside Ploi or the Makefile") is not something `skills/devops/SKILL.md` says (that lives in wp-infra and the ploi skill), so a run can fail the case for a clause the skill under test does not carry; the query says `make health env=production` but `health` takes no `env=` and probes every environment. Fix: drop the clause or add half a sentence to the devops health paragraph; drop `env=production` from the query. [whole-branch #9; security-sentinel I5]

## Note

1. `dist/Makefile.netdust:772` — the script's whole output is captured into `O` and printed at the end, so the section is silent for up to (1+8+20) × 8 s per environment on a hanging site; a `tee` to a temp file would stream it. [whole-branch #5]
2. `tests/test-makefile.sh:427` — the `bad()` message says "exits 1" where the `ok()` says "non-zero (make reports 2)". [whole-branch #7; the coder flagged it]
3. `dist/Makefile.netdust:672` — the `health:` doc comment was not extended to name exposed paths and now disagrees with the `help` line. [whole-branch #8]
4. A project with no `environments` key prints nothing under the heading and exits 0 (the other `health` sections behave the same way). [whole-branch #10]
5. TLS failures (expired certificate, hostname mismatch) collapse into `000` / `unreachable`; curl's exit codes 60 and 35 could be named. [security-sentinel I3]
6. Environment names are printed unescaped (`health-exposure:46,69`); a YAML key with an escape sequence reaches the terminal. The rest of `Makefile.netdust` prints environment names the same way. [security-sentinel I1]
7. `sed 's/\x1b…'` in the recipe is GNU-only (the suite's own `strip()` already relies on it); `deny all` is dead behind `return 404` in the example rule, the result is still 404. [security-sentinel I6, I7]
