
### 2026-08-19
- systemd `EnvironmentFile=` loads after `Environment=` and overrides it. Reading only a `.service` file's inline `Environment=` line gave me a wrong diagnosis (collie pointed at a dead socket). Read the `.env`, or verify from the process's actual behaviour.
- herdr sessions are separate servers with separate ID spaces — a bare `herdr` command targets the session the calling pane lives in, not the project's session. Creating topology without first checking `herdr session list` puts it in whatever session you happen to be sitting in. There is no move between sessions; the only fix is rebuild in the right one and close the wrong one.

### 2026-08-20
- `gate-check.py`'s task regex was `(T\d+)\b`, which cannot match `T07b`: `T\d+` stops at the digit and `\b` then demands a boundary between two word characters. Every `b`-suffixed task was invisible — skipped by the tier, files, test-author, proven-by and unit-test checks, and uncounted by the `<=4` cluster-size rule. Found on todai-client, where a FULL-tier security spec had three such tasks (T03b already shipped, T09b a Tier-A data-minimisation control) and still read `GATE: PASS`, while a 6-task cluster counted as 4. This is INV-4's own failure mode: a verdict reporting green while a named check never ran. When a checker's verdict looks too easy, test the PARSER against the corpus, not just the rules.

### 2026-08-23 (ntdst-core 5.0.0 spec-close)
- Implementer reports twice described `composer gate` as "lint → analyse → audits → unit" when the gate is `@syntax @test @guard @audit:deps` — no phpcs, no static analyser is even installed. A close-out must describe the gate from `composer.json`'s script, never from a generic pipeline; claiming a check ran that does not exist violates the verification-claims rule and misleads the next reader (this happened in two independent dispatches).
- An implementer used `git checkout -- <file>` to undo a falsifiability probe and reverted the implementation with it (caught, replayed, gate re-run). `git checkout -- <file>` is never an undo — it destroys uncommitted work indiscriminately. Probes are reverted by re-applying the recorded edit, or made in a scratch copy outside the repo.

### 2026-09-03 (josworld cpt-builder-singles spec-close)
- `hooks/pretooluse-guard.py` matches the TEXT of a Bash call, not its intent: a heredoc commit message, an inline python string, or a lessons paragraph that names a Makefile verb or quotes `git commit` was refused, four times in one session — the last time while writing this very lesson. Commit messages go to a file (Write tool) and `git commit -F`; multi-line edit scripts go to a file and run with `python3 file`. A guard that keys on quoted words teaches sessions to phrase around it — it should key on the command position, not on prose.
- The same guard refuses `git commit` / `git switch -c` on a rung branch and points at the Makefile verb, but the Makefile's `_ensure-flow` refuses without an `origin`. A repo with no remote cannot commit anything under the harness: verified work sat uncommitted until the operator added the remote and pushed the rungs by hand. Check `git remote -v` at intake and ask for the remote URL before starting, not at commit time.
- The Stop hook auto-committed `tasks/todo.md` in the middle of a fix-wave dispatch that also touched six tracked files; the implementer had to fold the commit back to keep the wave atomic. A hook that commits during a dispatch splits the diff the reviewer is about to read — it should stage nothing while a subagent is live, or commit only its own file at session end.
- `skills/building/SKILL.md` names `cluster-open` / `cluster-close` ledger events "the hook's tolerance reads", but no hook or bin script reads them (`grep -rn cluster-open` hits the skill alone). A behaviour cluster's intentionally red test therefore has no machine tolerance; the workaround was a `@group cluster-red` on the RED test and `--exclude-group cluster-red` in the implementers' suite line. Either implement the event in `subagent-stop.py` or state the group convention in the skill.
- `gate-check.py`'s cluster cap (<=4) refuses a plan-correction task added mid-build without a new cluster; the honest fix was to split the cluster (B1/B2), each with its own behaviour block and RED. Budget a spare slot when a cluster is planned at exactly four.
